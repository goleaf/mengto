# 10. Validation, Form Requests, Livewire Forms, Typed Data Contracts, and Error Handling

## Principal-agent role

You are the principal Codex implementation agent responsible for making every untrusted input explicit, normalized, authorized, validated, typed, and safely reported across HTTP, Livewire, API, file, import, and integration boundaries.

## Mission

Audit all input paths and error outputs. Consolidate reusable rules, use Form Requests and Livewire Form Objects appropriately, replace uncontrolled payloads with validated typed contracts, enforce domain transitions and database constraints, and standardize safe localized errors without exposing internal details.

This is not an audit-only, documentation-only, planning-only, or review-only task. Discovery and planning are mandatory intermediate phases. After updating the canonical plan, immediately perform the required implementation, tests, review fixes, documentation synchronization, commit, and safe push directly on `main`.

3. **Load governing instructions before work.**

5. **Do not ask the user questions.**
   - Resolve ambiguity through repository evidence: code, tests, database schema, configuration, logs available in the repository, local Git history, first-party documentation, and current runtime behavior.
   - Choose the safest non-destructive, testable, backward-compatible interpretation.
   - Record material assumptions in the plan or an ADR and continue.

10. **Finish documentation and Git work.**
    - Synchronize the plan, compliance matrix, changelog, and all affected first-party documentation with the final implementation.
    - Review the complete diff and staged diff for secrets, generated artifacts, unrelated changes, accidental deletions, and stale comments.

## Domain-specific guardrails

- Do not use validation as authorization or authorization as validation.
- Do not use a validation uniqueness check as the only concurrency protection; add a database unique constraint where the invariant requires it.
- Do not normalize passwords, cryptographic tokens, signed payloads, or user-authored content in a way that changes intended bytes.
- Do not pass entire request/component state arrays into model create/update methods.
- Do not expose internal exception messages, SQL, paths, tokens, or provider payloads to users.

## Required implementation scope

Complete all applicable work below. Treat the list as a minimum, not as permission to ignore defects discovered in the same scope.

- Inventory every untrusted input and map it to normalization, authorization, validation, typed mapping, persistence, and error behavior.
- Create or refine Form Request classes for substantial HTTP/API requests, including request-level authorization where appropriate.
- Create or refine Livewire Form Objects for substantial component forms; keep domain logic in actions/services and validate each mutation.
- Use inline rules only for genuinely small local interactions and custom Rule classes for reusable complex domain rules.
- Whitelist nested array keys, validate arrays and each element, enforce enum values, scoped uniqueness/existence, tenant ownership, date ordering, money precision, URL schemes, file content, and state transitions.
- Define explicit field-specific normalization for whitespace, Unicode, case-insensitive identifiers, email, phone, locale, money, dates, and URLs.
- Use validated data, explicit field maps, DTOs, or value objects rather than uncontrolled associative arrays and mass assignment.
- Add database constraints for critical invariants and safe data migrations where canonicalization reveals existing invalid data.
- Implement a consistent localized error taxonomy for web, Livewire, and API behavior with correct HTTP status codes and safe logging.
- Ensure invalid input causes no partial persistence, file writes, external calls, notifications, or other side effects.
- Create comprehensive tests for valid, missing, wrong-type, min/max, boundaries, enums, uniqueness, tenant scope, malicious strings, nested arrays, dates, money, URLs, files, localized errors, and mass-assignment protection.
