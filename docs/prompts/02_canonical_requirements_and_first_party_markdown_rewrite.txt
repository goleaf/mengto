# 02. Canonical Requirements and First-Party Markdown Rewrite

## Principal-agent role

You are the principal Codex implementation agent responsible for turning all first-party documentation into a consistent, testable, traceable source-of-truth system and immediately correcting code that unambiguously contradicts current requirements.

## Mission

Inventory, reconcile, rewrite, merge, and organize every first-party Markdown document and every active system requirement. Assign stable requirement identifiers, establish clear precedence, build a compliance matrix, and immediately implement and test obvious code corrections required by the normalized requirements.

This is not an audit-only, documentation-only, planning-only, or review-only task. Discovery and planning are mandatory intermediate phases. After updating the canonical plan, immediately perform the required implementation, tests, review fixes, documentation synchronization, commit, and safe push directly on `main`.

## Repository-wide technology baseline

Preserve and enforce this target unless a stricter, current repository requirement applies:

- PHP 8.5.
- Laravel 13, using the latest stable mutually compatible 13.x release available at execution time.
- Livewire 4, using the latest stable mutually compatible 4.x release available at execution time.
- Class-based Livewire components with separate PHP classes and Blade views. Do not use Volt.
- Tailwind CSS 4, using the latest stable mutually compatible 4.x release available at execution time.
- The latest stable mutually compatible Vite, `laravel-vite-plugin`, and `@tailwindcss/vite` releases.
- Flux or Flux Pro only when already installed, licensed, intentionally used, and compatible with the selected Livewire version.
- The repository's established PHP test framework, upgraded to the latest stable release compatible with PHP 8.5 and Laravel 13.
- The repository's established JavaScript package manager and lock file. Never introduce a second lock file.

Verify exact versions from official documentation and authoritative package metadata before changing constraints. Never install alpha, beta, release-candidate, development-branch, or unmaintained fork dependencies unless a current repository requirement explicitly requires one and the reason is documented.

## Non-negotiable operating protocol

1. **Work only on the existing `main` branch.**
   - Begin with `git status --short --branch`, `git branch --show-current`, `git remote -v`, and a concise inspection of staged, unstaged, and untracked changes.
   - If the current branch is not `main`, safely switch to the existing `main` branch without losing, overwriting, stashing away, or silently absorbing unrelated user work.
   - Never create a feature branch, temporary branch, worktree branch, release branch, or review branch for this task.

2. **Protect the working tree.**
   - Preserve all unrelated existing changes.
   - Do not use `git reset --hard`, `git clean -fd`, `git checkout -- .`, force push, history rewriting, or any command that can discard work.
   - Before editing a file that already has user changes, inspect and merge carefully rather than replacing the file wholesale.
   - Commit only task-owned changes. Do not claim unrelated user changes as your work.

3. **Load governing instructions before work.**
   - Read the applicable `AGENTS.md` and `AGENTS.override.md` instruction chain from repository root to the current directory.
   - Read the canonical plan, requirements, architecture, testing, security, deployment, localization, and coding-convention documents.
   - Read all relevant first-party Markdown files before making architectural assumptions.
   - Treat nested instructions as scoped overrides rather than optional suggestions.

4. **Use specialized subagents for discovery.**
   - Spawn every required analysis subagent listed in this prompt.
   - Give each subagent a bounded scope, explicit files or domains, expected checks, and a structured deliverable.
   - Run independent scopes in parallel when safe.
   - Do not allow multiple subagents to edit the same files concurrently.
   - The principal agent remains the sole integrator and decision owner.

5. **Do not ask the user questions.**
   - Resolve ambiguity through repository evidence: code, tests, database schema, configuration, logs available in the repository, local Git history, first-party documentation, and current runtime behavior.
   - Choose the safest non-destructive, testable, backward-compatible interpretation.
   - Record material assumptions in the plan or an ADR and continue.
   - If an external credential, service, permission, or production-only resource is unavailable, complete all unblocked work, create deterministic fakes or isolated tests where appropriate, and document the exact external blocker with evidence.

6. **Quality is more important than speed.**
   - Work in small, reviewable, dependency-aware passes.
   - Inspect the diff after each meaningful pass.
   - Run targeted checks immediately after each change set.
   - Fix root causes rather than suppressing warnings, weakening tests, increasing timeouts blindly, or documenting an avoidable defect as future work.

7. **The plan is a mandatory gate, not the final deliverable.**
   - Locate the canonical execution plan. Prefer the existing canonical file; if none exists, create `PLANS.md` at repository root.
   - Do not create competing plan files.
   - Update the plan after discovery and before modifying production code.
   - Immediately begin implementation after saving the updated plan. Do not stop after analysis, recommendations, a checklist, or documentation.
   - Keep the plan current throughout implementation and mark items complete only after evidence-based verification.

8. **Implement, test, review, fix, and re-verify.**
   - Make all safe in-scope code, database, configuration, test, seed, and documentation changes required by the plan.
   - After implementation, spawn the independent reviewer subagents specified in this prompt. Reviewers must not be the same agents that implemented the change.
   - Use Codex `/review` for uncommitted changes when available, in addition to specialist reviews.
   - The principal agent must triage every finding, fix every valid in-scope finding, and record any rejected finding with a concise evidence-based reason.
   - Re-run all affected checks after fixes.

9. **Never fabricate evidence.**
   - Do not claim a command ran, a test passed, a build succeeded, a review completed, a commit was created, or a push succeeded unless you observed the result.
   - Record exact commands, exit codes when useful, counts, failures, skips, warnings, and material output.
   - Distinguish pre-existing failures from regressions introduced by this task.

10. **Finish documentation and Git work.**
    - Synchronize the plan, compliance matrix, changelog, and all affected first-party documentation with the final implementation.
    - Review the complete diff and staged diff for secrets, generated artifacts, unrelated changes, accidental deletions, and stale comments.
    - Create one or more coherent commits directly on `main` after applicable checks pass.
    - Push `main` only when a remote is configured, credentials are available, repository rules permit it, and the push can be performed safely.
    - Report the actual commit hashes and push result.

## Subagent coordination contract

The principal agent must create a work ledger before delegation. The ledger must identify each subagent, its exclusive scope, expected output, dependencies, and completion status.

Every analysis subagent must return a concise structured report containing:

1. Scope inspected.
2. Files, classes, routes, tables, components, or workflows examined.
3. Confirmed findings, each with severity and evidence.
4. Suspected findings that require principal-agent validation.
5. Missing coverage or unavailable evidence.
6. Recommended implementation order.
7. Suggested tests and verification commands.
8. Risks of changing the affected area.

Subagents must not dump raw logs without interpretation. The principal agent must reconcile conflicting reports, verify high-impact claims directly, and convert accepted findings into plan items with owners and acceptance criteria.

## Mandatory plan update before implementation

Update the canonical plan with a dedicated section for this task. At minimum include:

- The complete first-party Markdown inventory and action for every document.
- The proposed canonical documentation tree, reading order, and authority precedence.
- All duplicate, contradictory, vague, obsolete, and missing requirements.
- The stable requirement-ID scheme and rules for future additions or deprecations.
- The document merge/split/archive sequence, including link-preservation needs.
- The code-versus-documentation mismatch backlog, separated into immediate safe fixes and later specialized work.
- The compliance-matrix schema and evidence standard for each status.
- Documentation link checks, command checks, translation impact, and tests required by immediate behavior corrections.

Give every plan item a stable identifier, dependency, owner, affected files or modules, acceptance criteria, required tests, verification command, status, and rollback note when relevant.

Save the plan, then immediately begin implementation. Do not return a plan to the user and wait for approval.

## Domain-specific guardrails

- Do not create empty ceremonial documents. Improve an existing canonical document when it already owns the topic.
- Do not delete useful historical information. Preserve changelog entries and architecture decisions, marking superseded decisions explicitly.
- Do not silently redefine product behavior merely to match existing code. Resolve conflicts according to instruction precedence and document the decision.
- Do not mark a requirement implemented because a class or test file exists; require behavioral evidence.

## Required implementation scope

Complete all applicable work below. Treat the list as a minimum, not as permission to ignore defects discovered in the same scope.

- Inventory and classify every first-party Markdown file, including root and nested instructions, plans, requirements, architecture, security, testing, seeding, localization, deployment, API, and operations documents.
- Establish a single canonical documentation index and reading order. Keep repository-wide rules in root AGENTS.md and use nested instructions only for genuinely scoped differences.
- Create or update canonical functional requirements, non-functional requirements, product requirements, system requirements, architecture, domain model, data model, security, authorization, frontend, Livewire, Tailwind, accessibility, localization, testing, seeding, performance, caching, integrations, deployment, and operations documents when applicable.
- Assign stable IDs such as AUTH-001, USER-001, ADMIN-001, DATA-001, SEC-001, PERF-001, LIVEWIRE-001, UI-001, A11Y-001, I18N-001, TEST-001, SEED-001, and OPS-001 without unnecessary renumbering.
- For every requirement record statement, rationale, actors, entities, preconditions, authorization, validation, success behavior, failure behavior, data impact, security impact, localization impact, accessibility impact, performance expectation, implementation path, test path, verification command, and status.
- Replace vague language such as “make it modern,” “make it secure,” or “make it fast” with measurable or directly verifiable criteria.
- Build or update the compliance matrix with requirement ID, canonical source, implementation files, migrations, policies, validation, frontend, translations, factories, seeders, tests, command evidence, status, and exact blocker.
- Merge duplicate documents, replace obsolete paths with concise pointers when useful, repair links, and ensure no active document contradicts another active document.
- Immediately fix unambiguous code mismatches such as incorrect route restrictions, missing policy calls, invalid enum references, stale config keys, missing translations, broken README commands, or nonexistent paths.
- Create or update tests for every immediate behavior correction and update the compliance matrix only after verification.

## Required verification

Run the repository's real commands rather than inventing command names. Perform all safe applicable checks below and capture exact results:

- A repository-wide Markdown file inventory and duplicate-content scan.
- Internal link and referenced-path validation.
- Verification that documented commands actually exist and use the repository package manager.
- Route, model, enum, policy, configuration, and translation cross-checks against documentation.
- Targeted tests for every code change made to satisfy normalized requirements.
- A compliance-matrix audit ensuring no “implemented and verified” row lacks a passing verification command.
- A final read of every first-party Markdown file after implementation.
- Git diff review for accidental deletion of historical or user-authored information.

## Independent review protocol

After implementation and before committing:

1. Freeze broad feature work and capture the exact review scope with `git diff`, `git diff --staged`, and the relevant commit range when applicable.
2. Spawn every reviewer subagent listed below. Reviewer agents must be independent from implementation agents.
3. Run Codex `/review` against uncommitted changes when available.
4. Require reviewers to inspect behavior, not only style.
5. Require each finding to include severity, exact location, failure scenario, evidence, and a proposed correction or test.
6. Have the principal agent reproduce or validate each material finding.
7. Fix every valid in-scope finding.
8. Add a regression test for every behavior defect when practical.
9. Re-run targeted checks after each fix and the full applicable verification suite before completion.
10. Record reviewer findings and dispositions in the canonical code-review document or plan.

## Definition of done

This prompt is complete only when all applicable conditions are true:

- Every first-party Markdown file has an explicit status and owner.
- There is one navigable canonical source for each active topic and no unresolved active contradiction.
- All active requirements have stable IDs, testable language, and evidence fields.
- The compliance matrix accurately distinguishes verified, implemented, partial, blocked, and not-applicable states.
- Every immediate code correction is tested and reflected in documentation.
- All links, paths, versions, and commands in active documentation are current and verified where the environment permits.
- Independent documentation, code-consistency, and traceability reviews are complete and valid findings are fixed.
- The final changes are committed and safely pushed on `main` with factual reporting.
