# 11. Maximum Appropriate Livewire 4 Modernization

## Principal-agent role

You are the principal Codex implementation agent responsible for modernizing every Livewire component to current Livewire 4 practices while minimizing hydration cost, securing every action, improving navigation and user feedback, and using advanced capabilities only where semantically correct.

## Mission

Inventory and refactor all Livewire components, forms, events, uploads, pagination, URL/session state, JavaScript integration, navigation, and rendering behavior. Remove Volt, keep class-based components with separate Blade views, minimize public state, eliminate hidden queries, and create a documented applicability decision for every significant modern Livewire capability.

This is not an audit-only, documentation-only, planning-only, or review-only task. Discovery and planning are mandatory intermediate phases. After updating the canonical plan, immediately perform the required implementation, tests, review fixes, documentation synchronization, commit, and safe push directly on `main`.

## Repository-wide technology baseline

Preserve and enforce this target unless a stricter, current repository requirement applies:

- PHP 8.5.
- Laravel 13, using the latest stable mutually compatible 13.x release available at execution time.
- Livewire 4, using the latest stable mutually compatible 4.x release available at execution time.
- Class-based Livewire components with separate PHP classes and Blade views. Do not use Volt.
- Tailwind CSS 4, using the latest stable mutually compatible 4.x release available at execution time.
- The latest stable mutually compatible Vite, `laravel-vite-plugin`, and `@tailwindcss/vite` releases.
- Flux or Flux Pro only when already installed, licensed, intentionally used, and compatible with the selected Livewire version.
- The repository's established PHP test framework, upgraded to the latest stable release compatible with PHP 8.5 and Laravel 13.
- The repository's established JavaScript package manager and lock file. Never introduce a second lock file.

Verify exact versions from official documentation and authoritative package metadata before changing constraints. Never install alpha, beta, release-candidate, development-branch, or unmaintained fork dependencies unless a current repository requirement explicitly requires one and the reason is documented.

## Domain-specific guardrails

- Do not use or introduce Volt; migrate existing Volt to class-based components with separate PHP and Blade files.
- Do not convert static Blade presentation into Livewire solely to increase Livewire usage.
- Do not store services, query builders, large collections, full model graphs, secrets, or safely derivable values in public state.
- Do not use `#[Locked]`, hidden inputs, or client-side state as authorization.
- Do not use async, streaming, polling, islands, persistence, or navigation without explicit race, lifecycle, accessibility, and test analysis.
- Do not invent attributes or directives; verify support in the exact installed Livewire 4 version.

## Required implementation scope

Complete all applicable work below. Treat the list as a minimum, not as permission to ignore defects discovered in the same scope.

- Inventory every Livewire component, form, route, Blade view, listener, event, upload, paginator, URL/session property, and JavaScript dependency.
- Migrate every applicable Volt component to a class-based PHP component and separate Blade view while preserving behavior and tests.
- Minimize public state, replace duplicated derived state with computed values, use stable IDs and `wire:key`, and keep sensitive/server-only data out of snapshots.
- Authorize and validate every mutation, listener, upload, download, sort/reorder, JSON response, and direct-call path immediately before sensitive work.
- Eliminate render-time N+1, repeated queries, unbounded data, and unnecessary `.live` requests; use deferred binding, `.blur`, `.change`, and debounced search appropriately.
- Use URL state for shareable filters/tabs/sort/pagination; session state only for private UI preferences; never store secrets or permanent business state there.
- Use lazy/defer/isolate/islands for independent expensive regions only after fixing SQL and measuring the benefit; provide stable accessible placeholders.
- Use precise loading targets, dirty/offline states, confirmation, duplicate-submission prevention, empty/error/success feedback, and focus handling.
- Audit `wire:navigate` and all custom JavaScript/Alpine integrations; implement idempotent initialization and teardown and safe persisted DOM behavior.
- Implement appropriate sorting, intersection, polling, streaming, renderless, JSON, JS, async, transitions, teleport, and persistence features only where approved in the applicability matrix.
- Create or update component-level PHP tests, action-security tests, query-budget tests, pagination/URL/session tests, upload/event tests, and browser tests for navigation/lifecycle/accessibility behavior.
- Create architecture tests that prohibit Volt and detect forbidden Livewire/Blade patterns where reliable.
