# 21. Measured Performance, Cache Architecture, Redis, Memcached, and Locks

## Principal-agent role

You are the principal Codex implementation agent responsible for improving application performance through evidence-based query, Livewire, asset, media, cache, lock, and bounded-processing changes rather than speculative caching.

## Mission

Capture reliable baseline metrics, fix inefficient SQL and state flow first, then introduce or repair cache entries with explicit ownership, scope, TTL, invalidation, stale behavior, and tests. Use Redis and Memcached only for distinct justified roles, add atomic locks for races and stampede prevention, and prove before/after improvements.

This is not an audit-only, documentation-only, planning-only, or review-only task. Discovery and planning are mandatory intermediate phases. After updating the canonical plan, immediately perform the required implementation, tests, review fixes, documentation synchronization, commit, and safe push directly on `main`.

## Domain-specific guardrails

- Do not cache inefficient queries before fixing them when a direct query/schema/state solution exists.
- Do not cache authorization-sensitive data without user/role/tenant/locale/version scope and precise invalidation.
- Do not use Redis and Memcached simultaneously merely to maximize technology usage.
- Do not rely on cache tags, locks, atomic operations, or serialization features unsupported by the selected driver.
- Do not claim performance improvement without comparable before/after evidence.
- Do not write brittle wall-clock tests where deterministic query/payload/memory budgets are possible.

## Required implementation scope

Complete all applicable work below. Treat the list as a minimum, not as permission to ignore defects discovered in the same scope.

- Capture a reproducible baseline for critical pages, APIs, Livewire interactions, queries, memory-heavy operations, frontend assets, and media.
- Fix N+1, repeated queries, missing indexes, unbounded reads, unnecessary columns, PHP-side aggregation/sorting, and pagination/chunking defects before adding cache.
- Reduce Livewire public state, request frequency, repeated rendering, polling, and snapshot size; use computed values, pagination, precise bindings, lazy/defer/islands only where measured and justified.
- Remove duplicate/unnecessary frontend entries/libraries and deliver size-appropriate optimized media while preserving behavior.
- Inventory all cache calls and implement a registry with explicit owner, key format, version, tenant/user/role/locale scope, TTL, stale behavior, invalidation triggers, fallback, and tests.
- Centralize cache-key construction where it reduces leakage risk; invalidate narrowly after successful writes rather than clearing the entire store.
- Use Redis for locks/counters/rate limits/sessions/queues/cache only when configured and justified; use Memcached only for distinct simple volatile cache needs.
- Implement atomic locks, idempotency, or unique constraints for expensive regeneration and race-sensitive work; prevent stampedes with locking or stale-while-revalidate behavior compatible with the repository.
- Use `Cache::touch` only when extending an existing entry’s lifetime is semantically correct and covered by tests.
- Make imports, exports, reports, cleanup, seed volume, and other high-volume operations memory-bounded, resumable, and idempotent according to queue/web-only constraints.
- Create query-budget, cache hit/miss/scope/TTL/invalidation/failure, lock concurrency, Livewire payload/request, bounded-processing, and asset-build regression checks.
- Repeat all measurements with the same data and methodology and document before/after results honestly.
