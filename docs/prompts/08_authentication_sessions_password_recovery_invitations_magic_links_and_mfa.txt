# 08. Authentication, Sessions, Password Recovery, Invitations, Magic Links, and MFA

## Principal-agent role

You are the principal Codex implementation agent responsible for securing and completing every account-authentication lifecycle while preserving intended invite-only, verification, recovery, and demo behavior.

## Mission

Audit and modernize registration, invitation acceptance, login, logout, session management, password reset, email verification, magic links, MFA, recovery codes, impersonation, account state, and demo access. Eliminate replay, enumeration, fixation, concurrency, and environment-safety defects and prove every flow with positive and adversarial PHP tests.

This is not an audit-only, documentation-only, planning-only, or review-only task. Discovery and planning are mandatory intermediate phases. After updating the canonical plan, immediately perform the required implementation, tests, review fixes, documentation synchronization, commit, and safe push directly on `main`.

## Domain-specific guardrails

- Do not weaken password, verification, MFA, CSRF, session, or rate-limit protections to preserve a broken legacy flow.
- Do not store newly issued one-time tokens in plaintext when secure digest lookup is feasible.
- Do not trust user-supplied role, tenant, company, owner, or recipient identifiers during registration or invitation acceptance.
- Do not expose whether an account exists unless the current product explicitly requires it and the security tradeoff is documented.
- Do not make demo credentials or bypasses available in production.

## Required implementation scope

Complete all applicable work below. Treat the list as a minimum, not as permission to ignore defects discovered in the same scope.

- Document and implement explicit state machines for account, invitation, reset, verification, magic-link, MFA, and recovery-token lifecycles.
- Regenerate session identifiers after authentication, invalidate sessions correctly on logout, regenerate CSRF tokens where appropriate, and enforce secure cookie/session configuration.
- Implement consistent login and account-state checks for active, inactive, blocked, suspended, deleted, unverified, and MFA-required users.
- If invite-only is required, disable every open-registration path and enforce secure invitation acceptance at the current route such as `/invite/{token}`.
- Generate cryptographically secure tokens, store secure hashes when feasible, bind tokens to purpose/owner/recipient, enforce expiry/revocation, and consume atomically.
- Prevent replay and concurrent double use with transactions, conditional updates, unique constraints, or locks as appropriate.
- Secure password reset, password confirmation, signed email verification, MFA enrollment/challenge, single-use recovery codes, and sensitive account changes.
- Apply purpose-aware rate limits to login, registration, invitation creation/acceptance, reset, verification, magic links, MFA, and recovery flows without creating account enumeration.
- Audit notifications, logs, URLs, API responses, and exceptions so complete tokens and secrets are never exposed.
- Gate demo users and login helpers to explicit local/demo environments and add production-safeguard tests.
- Create comprehensive feature/Livewire tests for success, invalid credentials, blocked state, session rotation, logout invalidation, expiry, revocation, replay, concurrency, wrong recipient, wrong tenant, rate limits, MFA, recovery, and demo safeguards.
